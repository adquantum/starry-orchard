# Starry Orchard · 星界果园

星界果园是一个使用 **Godot 4.5** 开发的非官方项目，以 **Wizard101 的回合制卡牌战斗规则**为参考，结合角色养成、场景探索与多人相关系统。本项目不代表 Wizard101 官方，也没有声明与其开发商或发行商存在合作关系。

## 当前代码包含什么

以下功能依据本仓库实现核实，表示代码中已有相应机制，不代表所有场景、资源与联网部署均已完成验收。

- **回合制卡牌战斗**：战斗状态、行动选择、回合推进、伤害/治疗与事件流分离，核心位于 `scripts/battle_v2/core`。
- **魔豆与超级魔豆**：普通魔豆、强化魔豆（Power Pip）和系别魔豆有独立类型；回合生成、支付计划、系别适配与消耗由资源/费用结算器处理。魔豆槽位上限为 7，不能把所有系别的超级魔豆都简单视作相同费用。
- **牌组与手牌**：牌组配置、洗牌、初始抽牌、补牌、出牌与弃牌；手牌上限为 7，状态模型位于 `scripts/battle_v2/model/deck_state_v2.gd`。
- **刃、盾、陷阱与虚弱**：状态匹配、倍率结算、穿透与消费顺序已有实现；也包含吸收、棱镜、持续伤害/治疗等相关处理。具体行为以费用、行动、伤害和状态结算器为准。
- **系别**：火焰、冰霜、风暴、神话、生命、死亡、平衡的标识、主题与规则匹配；部分模型还包含全系和暗影资源的处理。
- **多人和账号相关系统**：城镇主机/客户端连接、外观同步、游戏服务协议以及账号、角色和进度存储代码，见 `scripts/fusion_3d/town_network.gd`、`scripts/server` 和 `server`。这些代码不构成公网部署或并发容量保证。
- **探索与表现**：星界果园、寒冰岛等探索逻辑、角色换装、战斗视觉表现和客户端增量更新启动门，分别位于 `scripts/worlds`、`scripts/fusion_3d`、`scripts/updater`。

## 公开范围与授权

此目录用于公开代码协作，保留 GDScript、文本场景、shader、服务端代码与必要项目配置。**PCK、增量包、模型、贴图、音频、字体、玩家数据、凭据和第三方插件不进入此仓库**；来源尚未确认的资源目录数据也不公开混入。

公开代码不等于公开素材授权，也不等于已经授予开放许可证。当前**未添加 MIT、GPL 等开放许可证**，没有授予第三方游戏素材的再分发或商用权。指定核心协作者的仓库写入权限由项目维护者另行配置；公开仓库中的代码可被下载或创建个人副本，但只有获得权限的协作者可以直接写入本仓库。

需要 `dialogue_manager` 等第三方插件时，应通过获授权的私有协作副本恢复并遵守原有许可证。本仓库不包含该插件。

## 开发环境与项目入口

- 项目配置：`project.godot`；内部名称仍为 `Arcane Academy Duel`。
- 本机验证的引擎：`4.5.1.stable.official.f62fdbde1`，项目配置为 Godot 4.5 / Forward Plus。
- 主循环：`ClientUpdateTree`，实现于 `scripts/updater/bootstrap.gd`。
- 入口：`scripts/updater/startup_gate.tscn`；启动门允许进入业务后加载 `scenes/fusion_3d/studio_boot.tscn`，随后进入账号界面。
- 账号服务：Python 3.11+ 和 SQLite；生产 HTTP 依赖见 `server/requirements.txt`。开发时使用全新的测试数据目录，例：`python server/account_server.py --host 127.0.0.1 --port 8787 --data <新的测试目录>`。

## 源码 + 基础 PCK + 增量链协作

资源通过私有协作渠道交接，Git 负责源码。完整客户端不是只有一个基础 PCK：已检查的本地发布清单为 `StarryOrchard-Client-Hotfix-20260929-08/manifest.json`，`base_id` 为 `win-frost-orchard-20260923-01`，`release_seq` 为 6。

已核验基础包和清单内 **91 个增量包**的大小/SHA256，合计 **2,490,161,355 字节**。现有启动门按“基础包 → 清单列出的增量顺序”组成覆盖视图，后加载的同路径内容覆盖前面的内容。合并后港城模型的导入映射存在；不能仅凭旧基础包目录判断完整客户端缺失资源。本次未重新验证发行清单签名，也尚未完成整个游戏以最新源码运行的验收。

源码协作的建议步骤：

1. 克隆此代码仓库，通过私有渠道获取与清单一致的基础 PCK、全部增量包及必要配置；保留相对路径，并按交接清单校验文件。
2. 在独立开发副本中生成安全的资产视图，保留模型/纹理导入映射及其缓存目标，过滤会接管源码的旧脚本/场景重定向和编译代码。当前已有 PCK 读取/子集工具，但仓库尚未交付完整的源码启动器。
3. 在业务 `preload` 和 autoload 加载前挂载资产；当前源码中的安装更新信息默认缺省，不会自动把发行包当作开发资源挂载。
4. 通过修改一个源码行为并观察结果确认源码实际生效，再进行账号界面、星界果园、寒冰岛、换装与战斗测试。不能只看到启动画面就认定源码成功接管。

`load_resource_pack(..., false)` 本身不足以保证源码优先：发行包里的新增 `.gd.remap` / `.tscn.remap` 仍可能把加载导向旧 `.gdc` / `.scn`。挂载太晚也不能更换已经预载的资源。[Godot 的资源包文档](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_pcks.html)说明了覆盖顺序与预载时序；[ProjectSettings 文档](https://docs.godotengine.org/en/4.5/classes/class_projectsettings.html#class-projectsettings-method-load-resource-pack)说明了 `replace_files` 的含义。

**运行时资源包不等于编辑器原始资源目录。** 仅有导入后的封包不足以完整编辑原模型/贴图；场景编辑、资源导入或重新导出仍需要相应的私有原始运行资源。源代码中的 UID、导入配置、实际重绘 PNG、材质槽位映射和原 alpha 必须保持对应，不能用旧模型贴图替代缺失重绘资源。

当前交接的核心源码快照也不是完整可运行游戏；它包含缺失资源清单和材质映射。完整启动方案、当前场景的全部资源闭包与视觉一致性仍需在隔离副本中验收。资源可使用私有分包，或在确认平台支持、配额及资源授权后选择 Git LFS。
